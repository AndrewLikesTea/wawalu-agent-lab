Issue #2577: Complete the Social publishing path with submitting, failure, and success states

## Most of this path already shipped — what was missing was the middle

I read the publishing path before editing, and most of the issue's three states were
already implemented and tested by sibling work. Not re-landed here:

- **Duplicate-submit suppression** — the `publishing` flag in `mountSocialFeed` drops a
  submit that arrives while one is in flight. Covered by
  `tests/social-composer-publish-race.test.js` and `tests/social-publish-confirmation.test.js`.
- **Failure state** — an inline error in the composer's own `#social-notice` region (not a
  page-level banner), the whole draft preserved, and a real `<button>` Retry. Covered by
  `tests/social-publish-confirmation.test.js`.
- **Success state** — focus moves to the confirmation, which names the outcome in words and
  links to `/post.html?id=<the id the API returned>` via `postPermalink`/`postDetailHref`.
  Covered by `tests/social-publish-confirmation.test.js`.
- **The image-post People action** — `See <name>'s image posts on People`, built with
  `profileHref`. Same file.

The gap was the state **between** the press and the outcome. `#social-notice` was *emptied*
when a request left, so the only thing on the page that said a publish was happening was the
submit button relabelling itself to "Publishing…" — a label change on the element the
reader's own focus is already sitting on, which assistive technology announces
inconsistently, and which says nothing at all to a reader who has tabbed away.

## What this change does

`showPending()` replaces the old `clearNotice()` at the moment the request leaves. It writes
the in-progress state into `#social-notice` — the same region both outcomes are written in,
`role="status" aria-live="polite" aria-atomic="true"`, and already named in the submit
button's own `aria-describedby`, so the sentence arrives politely, whole, and attached to the
control that started it. It is a filled chip reading **Publishing** plus a sentence saying
the post is on its way and that pressing again sends nothing.

It **overwrites** the previous outcome rather than clearing it, which keeps the property the
old code was protecting: a retry never runs under a region still reading "Not published". One
state at a time, and it is always the current one. No focus move — a live region speaks
without being visited, and the reader is left standing on the button they pressed.

## Deliberate deviation: the submit control is still not disabled

The issue asks me to disable the submit control while a publish is in flight. I did not, and
this is a considered decision rather than an omission:

- The issue's actual requirement — "a second activation while in flight must not send a
  second request" — is already met by the handler's guard, and the new test proves it across
  all four routes into the form (the button, a second button press, implicit submission from
  the single-line display-name field, and the post field's Cmd/Ctrl+Enter shortcut).
- Disabling is not what stops any of those routes; the guard is. The attribute would buy
  nothing.
- #2370 deliberately chose not to disable, with the rationale recorded in `src/social.js`: a
  disabled button drops the focus it was pressed with and removes itself from the tab order
  mid-interaction. Two shipped tests assert `disabled === false` during flight, one of them
  named for it. Overturning that would be a regression in the same area the issue is trying
  to improve.

I have instead made the in-flight state *legible*, which is the accessibility outcome the
"disable it" instruction was reaching for.

## Styling

One new rule, `.detail-state-chip-pending`, in the existing chip family — no new custom
property, no new component class. A filled wash, as the design direction requires of a state
happening now, with the word in the label so the signal is never colour alone. `styles.css`
had 346 bytes of headroom against its gate (not ~15 — that figure is stale); this spends 87
and leaves 259. `verify:build` passes with `styles.css` at `delta -0.3 KiB`.

## Which criteria rest on tests, and which on the stylesheet

**Assertion-backed behaviour** (`tests/social-publish-progress.test.js`, plus the two amended
files):

- The in-flight state is present, visible, not the success surface, told by exactly one chip
  carrying the word, and carries the explanatory sentence.
- The region is `role=status` / `aria-live=polite` / `aria-atomic=true`, exists exactly once,
  and is named in the submit button's `aria-describedby` — the "adjacent to the publishing
  action" requirement, asserted in the accessibility tree rather than by eye.
- Focus stays on the submit button during flight, and the region never becomes a tab stop
  (`tabindex="-1"`, absent from `tabSequence`).
- Four routes into Publish post, one request. Asserted on the request count and the
  `disabled` property — **not** on focus having moved, because disabling does not blur in this
  harness and such an assertion would pass for free.
- The in-flight state is replaced by both outcomes, and neither outcome sits under it.
- **New coverage:** the failure half through the *real* media wiring, for both image paths —
  the file picker and a Paint handoff. The pre-existing failure tests stub `getMedia`/
  `clearMedia`, so "the image survived" was asserted about a variable the test owns. Here the
  image goes in the way a visitor puts it there, and the evidence it survived is that the
  retry's POST body carries the same `image.data` and the same `alt`. Caption, display name,
  description, preview `src` and the media panel are all asserted unchanged, the composer is
  asserted still open, and Retry is asserted to be a real tab-reachable `<button>`.

**Stylesheet-level only** (this harness models no layout, so these are not provable by
assertion here):

- Narrow- and wide-viewport legibility. No module on this page reads `matchMedia` or
  `innerWidth`, so a viewport shim would assert only itself. The chip reuses the shipped
  `.detail-state-chip` geometry, which the composer already renders at both widths.
- Contrast is verified by computation rather than by rendering:
  `.detail-state-chip-pending` is added to the existing 4.5:1 pairings list in
  `tests/social-publish-confirmation.test.js`, which reads the declared `color` and
  `background` out of `styles.css` (this pairing computes to 8.3:1). That proves the declared
  values, not the painted pixels.
- The visible focus ring on Retry comes from shipped `.feed-status-action` rules; the test
  proves the control is a tab stop, not that the ring paints.

## Two amended tests

- `tests/social-publish-confirmation.test.js` — the in-flight test asserted
  `region.hidden === true` and `textOf(region) === ""`. Those assertions encoded the behaviour
  this issue changes, so they now assert the region names the in-progress state and no longer
  names the previous failure. Its title changed from "the button carries the state alone".
- `tests/social.test.js` — one wait was `waitFor(() => !notice.hidden)` followed by an
  `is-success` assertion. The region is now visible from the moment the request leaves, so that
  wait would return mid-publish and assert against the in-progress state. It now waits on the
  settled state, which is what it meant.

## Unresolved, not addressed here

The confirmation's link reads "Open the post's permalink" rather than the issue's literal
"Open post". I left the shipped wording: it is pinned byte-exact by an existing test, it is
the same phrase `/post.html` uses for the same address, and renaming it would be a copy change
dressed as a state change. If the shorter label is wanted, it should be one deliberate change
across both surfaces.
